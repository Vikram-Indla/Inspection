## Goal

`Shell` rendered the page title as `<Heading level={2}>`, so no route using it had
an `h1`. Promote it to level 1 without creating duplicate `h1`s or heading skips.

## What changed

| File | Action |
| --- | --- |
| `components/Shell.tsx` | `<Heading level={2} visual="display">` → `level={1}` |
| `components/ContextualAiPanel.tsx` | `<h3>` → `<h2>` |
| `app/(app)/reviews/[id]/page.tsx` | Shell `title={…}` → `title=""` |

Three lines. One reaches 88 routes.

## What it actually achieved, measured

```
107 <Shell> call sites
 88 pass a non-empty title  → now render an h1 (were h2)
 19 pass title=""           → still no h1 from Shell
```

Verified in the browser:

```
/planning   h1 1 ("Planning")                 main 1  outline H1 → H2 → H3   0 violations
/visits     h1 1                              main 1  outline H1 → H2 → H2   0 violations
/reviews    h1 1 ("Inspection review queue")  main 1  outline H1             0 violations
/operations h1 0  ← one of the 19 title="" routes      outline H2 → H2 → H2   0 violations
/factories  h1 0  ← its main render passes title=""
```

**The 19 remaining are not a shell problem.** They deliberately pass `title=""`
because their content owns the page heading — the established convention, used by
`/execution`, `/analytics` and `AdminDestinationFrame`. Some of them genuinely
have no `h1` anywhere (`/operations`, `/factories`), and each needs a per-route
decision about whether the shell or the content should carry it.

## The regression this change introduced, caught by testing for it

Promoting the shell title from h2 to h1 turns any content heading that began at
h3 into a **skip**. `/visits` went from a valid `H2 → H3 → H2` to an invalid
`H1 → H3 → H2`, and axe's `heading-order` rule flagged it:

```
before the fix   H1 → H3 → H2 → H2   heading-order: 1 violation
after the fix    H1 → H2 → H2 → H2   heading-order: 0
```

The cause was **`ContextualAiPanel.tsx:39` hardcoding `<h3>`** — the legacy AI
panel, already in the retirement ledger, superseded by `ai-advisory`/`AdvisoryStrip`
which correctly uses `level={2}`. One line fixed it on all **6** of that
component's surfaces, and h2 is the right level: it is a page-level section, the
same as its replacement.

**This is the whole reason the change was tested rather than assumed.** A
`heading-order` skip is not a WCAG AA failure — axe's WCAG tags stayed clean
throughout — so nothing but the best-practice rule would have reported it.

## A conflict I diagnosed wrongly, and reverted

I read `AccessState` as a second source of `h1` and `<main>` on six routes,
because six components matching `*AccessState` are used inside a `Shell`. I added
a `standalone` prop to it and then checked the import graph:

```
importers of components/AccessState   2   — app/launch/error.tsx, app/launch/no-workspace/page.tsx
both inside a Shell?                  no  — "Shell" appears only in a comment
the six *AccessState wrappers         render neither <main> nor h1
```

The wrappers share a naming pattern with `AccessState` and nothing else. The
conflict did not exist, so the prop solved nothing and was unused API on a
primitive — **reverted in full** (`git diff` on that file is empty).

**A filename grep is not an import graph.** I had the right instinct to check
before shipping and the wrong evidence when I started.

## One real defect fixed on the way

`/reviews/[id]` computed `ws.title.replace("{factory}", …)` **twice** — once in
the route for the shell title and once in `review-workspace` as its `h1` — so the
page rendered the same title in two places. Pre-existing, and my change would
have made it two `h1`s. Fixed by passing `title=""`, which follows the existing
convention, removes the duplicate title, and leaves the workspace's heading and
its status chips together where they belong.
