## Decisions

**`/field` is not an unmigrated SAQEEL surface. It is a different design
system.** `app/(app)/field/layout.tsx:30` links `/saqeel-ds/saqeel/styles.css`
from `public/`, which imports its own `tokens/{fonts,colors,typography,layout}.css`
plus a `components.css`. Its type scale has **thirteen** steps — 28 · 22 · 17 ·
15 · 14 · 13 · 13 · 12.5 · 12 · 11.5 · 30 — none of which are SAQEEL's nine, and
that is where every off-scale size on `/field` comes from.

**So the sweep was not started.** Migrating 38 files onto type primitives while
that stylesheet redefines `--font-*` and `--type-*` for the whole subtree would
be 38 files of work against a live override, and would fix neither the fonts nor
the scale. Raised for an owner ruling instead (WEB-002 §1). **Owner ruled: fonts
only for now.**

**The real defect was a runtime dependency on Google Fonts.**
`tokens/fonts.css` is two lines:

```css
@import url('https://fonts.googleapis.com/css2?family=IBM+Plex+Sans…&family=IBM+Plex+Mono…');
```

`app/layout.tsx` deliberately does the opposite, with the reason written in the
file: it self-hosts through `next/font/local` because *"Next.js dev/build must
not depend on … environments hit an unhandled Event from next/font/google's
fetch failure."* **The field channel therefore carried a network dependency the
rest of the application had already removed — on the one surface most likely to
be offline**, and one that registers a PWA.

Putting `var(--font-plex-arabic)` first means `/field` renders from the app's own
bundle and only reaches the Google-loaded literals if that is somehow absent.

**`--font-mono` was deliberately left leading with `"IBM Plex Mono"`.** The field
DS uses a genuine monospace for machine identifiers, which is a *design*
decision, not a font defect. Only `var(--font-plex-arabic)` was appended before
the generic — matching the reasoning already written into `app/tokens.css`, so
Arabic glyphs inside an identifier get the product face instead of an arbitrary
OS fallback. **Latin identifiers render exactly as before.**

## Two measurement corrections, both mine

**1. `document.fonts.check()` does not tell you whether text renders.** It
reports the document's `FontFaceSet`. My first probe had it return `false` for
`"IBM Plex Mono"` and I reported the font as "not loaded, 16 elements render in
a font that doesn't exist". **Wrong.** A width comparison against the real
element showed `as declared 247.50 == "IBM Plex Mono" alone 247.50`, distinct
from `ui-monospace` 209.84 and `Consolas` 226.80 — the font was rendering
perfectly, supplied by the Google import.

**2. A canvas `measureText` probe silently mis-parses a quoted family.** The
`ctx.font = '400 16px "IBM Plex Mono"'` form returned the bogus-family baseline,
which is what made the first claim look confirmed. **Measure by laying out a real
span with the element's own computed properties, not by canvas.**

The verification that actually held: build a hidden span, copy the element's
`font-size`/`weight`/`letter-spacing`/`font-variant-numeric`, and compare widths
across candidate families.

**This is a visible change and it is not neutral.** The two faces have different
metrics — measured on identical text at 16px, `IBM Plex Sans` 157.30 vs the
self-hosted `IBM Plex Sans Arabic` **175.23**, about **11% wider**. 129 elements
changed Latin face.

It is defensible on WEB-014 §2.0 — *"One typeface — IBM Plex Sans Arabic, and
nothing else"* — and it removes the offline risk. But it is a design change, not
a repair, and it is recorded as such.

Roughly a third of the remaining 734 belongs to a design system the sweep is not
migrating.
