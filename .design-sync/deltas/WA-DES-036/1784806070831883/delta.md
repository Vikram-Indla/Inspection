## Critical structural finding

**Two materially different `/planning` realities exist, and the design matches neither fully:**

1. **Canonical `/planning`** (default, no query param) is `CD-020 / SCR-WEB-100` — a **list-first visit-management surface**: RBAC-gated (`business_staff` only), KPI/status tabs with live counts, a 12-field URL-state filter bar, a 22-column canonical visit table, CSV export, refresh, pagination, and a draft-continuation section. Per its own header comment, this supersedes the design's tabbed-methods concept entirely: *"Legacy routes (`/planning/bulk`, `/single`, `/immediate`, `/plans`) are untouched."* **None of this list-first surface is depicted anywhere in the design page.**
2. **`PlanningPreview.tsx`** (`?wa_preview=1`, env-flagged) is a deliberately reduced surface built specifically to approximate the design's "Methods" home: effective-package banner, 3 method cards (bulk/single/immediate), a drafts table. It carries `data-saqeel-design="WA-DES-036"` — an explicit design-traceability marker. **This is the only real code surface worth comparing item-by-item against the design**, and is what the rest of this delta targets.

The design page itself is a **single-page tabbed SPA** (segmented control: Methods / Bulk / Single / Immediate / Plans, switched via client `state.screen`, all in one `.dc.html` file). The code's real navigation model is **multi-route** (`/planning`, `/planning/bulk`, `/planning/single`, `/planning/immediate`, `/planning/plans` are separate pages). The design's in-page tab-switching does not exist in the shipped app and, per the code's own comment, is a settled architectural decision, not a gap.
