ROUTE_LIFECYCLE_AND_OWNERSHIP_DECISION — non-product annotation (verified in repository 2026-07-14)
1. The product contract defines SCR-WEB-150 at /planning/:id/review. 2. That route is not implemented. 3. /planning/plans/:id is the post-publication, read-only plan drill-down. It receives no review-mode editing and no publish controls — this design places none there. 4. The current bulk flow keeps its staged selection/configuration in client/session state and publishes directly from /planning/bulk/review. 5. The bulk plan and child visits do not exist before the publish RPC; the RPC creates and publishes them in one transaction. 6. The single flow also publishes directly from its wizard; it creates a draft plan only after publish is submitted and can resume a partially completed write sequence (resume_visit_plan_id, verified in single/actions.ts). 7. There is therefore no route-addressable, persisted Validated plan that can truthfully supply /planning/:id/review before publication. 8. The reconciliation row mapping CD-025 to /planning/plans/:id ("Consolidated") is stale and does not override observed runtime behavior. 9. Immediate planning creates a published Visit directly and intentionally creates no Visit Plan — it does not pass through CD-025. 10. No planning-specific maker-checker/approver workflow is proven by the runtime. Package maker-checker behavior is not evidence of plan approval behavior.
Position taken: a route-neutral staged Plan Review & Publish workspace. No final URL, persisted draft identifier, handoff mechanism or approval queue is invented. The visible review reference (SR‑0142) is sample content, clearly labelled temporary, never a persisted plan ID. HANDOFF_BLOCKED until governance chooses and implementation proves one coherent model: (a) persist Draft/Validated plan records before review and use a real plan ID, or (b) retain an ephemeral staged review with an approved non-ID route and explicit recoverability semantics. Route, lifecycle and CD-024→CD-025 handoff ownership stay blocked in the manifest; STM-PLAN-001/002 remain the canonical transitions and are not weakened here.
Current-screen critique — 3 highest-cost decision failures (bulk review, single wizard, plan detail; read 2026-07-14)
1 · Configuration, assignment, validation and irreversible publication collapse into one screen and one click. On /planning/bulk/review the same surface where the planner is still editing is the surface that commits; there is no stable moment where the full consequence set can be inspected before the boundary. Cost: irreversible commits made while attention is on editing, not on consequences.
2 · No explicit consequence model exists anywhere. Neither flow states, before commit, exactly what will be created (plan/visits/assignments), what will be locked (package version, window), what is only queued (notifications), and what will NOT happen. Cost: planners over-read publication (assume delivery, acceptance) or under-read it (miss the visit count after scope reduction).
3 · The single flow's step sequence can half-complete while looking like one action. publishSingleVisit writes plan → visit → assignment → status → notification sequentially; a failed later step leaves earlier records present, surfaced only as a retry banner. Cost: "published" is ambiguous — the planner cannot tell a committed plan from a stranded partial one without understanding the step ledger.

Focus ring: 2px offset ring visible on dark (#7C6CFF on #0A0A14) and light (#6B57F0 on #FFFFFF). Failed submit: focus → error summary (role=alert, tabindex="-1"); each entry anchors to its row; return from edit lands focus on the corrected section heading (S28) with a polite "assignment updated — review continues". Success: focus → completion heading (5i). No modal is used, so no focus-restoration contract is owed. role="status" (polite): validating, revalidating, publishing progress, scope-count changes ("scope reduced — 10 of 12 factories"). role="alert" (assertive, once, never duplicated): blockers on submit, stale/concurrent change, transaction failure. Disabled publish carries its reason in visible text and aria-describedby. Disclosure widgets announce expanded/collapsed. Reduced motion: no spinner rotation theatre beyond opacity, no scroll animation, instant ledger updates — object continuity preserved. Conflict/selection cues are always glyph + text, never color alone.
Research ledger — adopted / rejected (frames cited)
GOV.UK — Check answers (design-system.service.gov.uk/patterns/check-answers/): one final page restating every answer with a change link per section, before an irreversible submit. Adopted: object sections with per-section "Change" links carrying hidden context (5a). Rejected: generic government styling; question/answer phrasing — Saqeel objects are factories/visits/packages, not form answers.
GOV.UK — Confirmation pages (…/patterns/confirmation-pages/): confirm only what happened, state what happens next. Adopted: completion panel with committed counts and truthful next destination (5i). Rejected: green panel claiming delivery/receipt; invented reference-number persistence; support contact — none exist.
GOV.UK — Error summary (…/components/error-summary/): focused summary, per-error links, input preserved. Adopted verbatim (5j). Rejected: nothing material.
WCAG 2.2 — Focus Order (w3.org/WAI/WCAG22/Understanding/focus-order.html): focus follows meaning and operability. Adopted: reading order = mandated narrow order; summary→row→restoration transfers (5j, S28). Rejected: sticky action bars that trap or reorder focus.
WCAG 2.2 — Status Messages (…/status-messages.html): status conveyed without focus stealing. Adopted: polite status for progress/scope counts, assertive alert only for actionable failures, no duplication (5g). Rejected: announcing every state change assertively.
Saudi DGA — web accessibility (dga.gov.sa/en/digital-knowledge/web-accessibility-disabilities-and-elderly-people): operability for disabled and elderly users. Adopted: ≥44–48px targets, plain-language consequence copy, glyph+text status. Arabic-first is NOT sourced here — binding Saqeel baseline (DEC-011). Rejected: nothing in scope.
PostgreSQL — Transaction Isolation (postgresql.org/docs/current/transaction-iso.html): a transaction guarantees atomicity of its own writes, not the freshness of reads made before it began. Adopted: bulk copy separates "created together or not at all" (true, RPC) from "checks re-run before publish; a change in that final moment is not caught" (5a readiness; S11/S18). Rejected: any "concurrency-safe" or "rechecked inside the transaction" claim.
