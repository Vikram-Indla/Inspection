Flagged AR/EN inconsistencies and internal contradictions (unresolved in source, indexed as written, not resolved by this pass):
- VIS-BR-078/079 — Create Visit Schedule "Period From" / "Period To" validation text is internally inconsistent: AR states "الفترة من" يجب أن تكون > "الفترة إلى" (From must be greater than To) and "الفترة إلى" يجب أن تكون < "الفترة من" (To must be less than From) — both restate the same (backwards-looking) inequality with no stated upper bound relationship that reads as a normal date range; also carried over from the prior pass's VIS-BR-044/045 flag, now landing at these row numbers.
- VIS-BR-139 — UC002 target-establishments-list edit/replace behavior differs between AR and EN: AR BC006 says an edit/replace of the target list applies changes only to establishments that have NOT yet had a visit executed within the specified period; EN BC005 says uploading a new file cancels any previously saved target-establishments list for the same period outright. These are materially different behaviors, not a translation variance — carried over from the prior pass's VIS-BR-062/063 flag.
- VIS-BR-142 — UC002 highlighting-on-change rule differs between AR and EN: AR BC009 only requires establishments newly ADDED to the list to be highlighted in orange; EN BC008 additionally requires establishments EXCLUDED from the list to be highlighted in RED — the red-highlight-on-exclusion requirement appears only in the English text. Carried over from the prior pass's VIS-BR-066 flag.
- VIS-BR-140 — UC002 BC006/BC007 (AR) and BC006 (EN) both instruct the system to reject unregistered establishments in an uploaded file "بالرسالة الآتية ERR003" / "message (ERR003)", but no ERR003 message text is defined anywhere in the document — the only Errors-section message actually defined under UC002 is ERR001 (a different, unregistered-establishment-in-file message with its own literal text). ERR003 is a dangling reference with no defined content.
- The AR business-rule numbering for UC002 runs BC001–BC010 (10 items) while the EN numbering for the same use case runs BC001–BC009 (9 items), because AR carries a standalone BC002 ("system validates data accuracy/duplication/mandatory fields against the DB") that EN folds into the main-flow narrative instead of giving it its own BC number — this pass indexes by AR position and notes the EN equivalent inline per row.

Visit priority order (VIS-BR-023, AR): تنفيذ جزاء (Penalty Enforcement) > بلاغ (Complaint) > خدمية (Service) > متابعة/انتهاء مهلة (Follow-up/Grace Expiry) > رقابية (Regulatory). The EN text under the same BC001 lists a different order: Penalty Enforcement > Complaint > Follow-up (Grace Period Expiry) > Service > Regulatory — Service and Follow-up are swapped between AR and EN. Indexed as written at VIS-BR-023, not resolved.

One active visit per establishment at a time (VIS-BR-024). Annual visit requirement — every establishment must be visited at least once per calendar year, Jan 1–Dec 31 (VIS-BR-036).

On the four "expert judgement only" Jira stories under review (INSP-180/181/198/226 — visit drafting, single-visit publish/create, bulk visit changes, inspector assignment): real, named business rules were found for visit-draft validation (mandatory-field/license-match/priority rules — VIS-BR-006, VIS-BR-023, VIS-BR-042, and the Create Visit form fields at VIS-BR-065–077), for bulk visit cancellation (UC001 main-flow step 10/11 — user selects "one or more visits" and clicks Cancel — VIS-BR-051, alongside the Cancel-restricted-to-New-status rule at VIS-BR-043), and for capacity-based inspector assignment (VIS-BR-025 through VIS-BR-030 — per-inspector maximum visit cap set by the Branch Manager with redistribution, same-city-same-day grouping, one-city-per-day cap, max two large establishments per inspector per day, priority to inspectors who have not previously visited the establishment, and a balanced-distribution requirement). No rule anywhere in the document names or describes an "idempotency" mechanism for single-visit publish/create — the only safeguard against duplicate/accidental creation is a confirm-then-success dialog pair (VIS-BR-040/BR-041/BR-044/BR-045, MSG001 "Are you sure…" / MSG002 "created successfully"), which is a UX confirmation step, not an idempotency guarantee (no idempotency key, no duplicate-submission detection, no dedupe-on-resubmit rule is stated anywhere in the source).
