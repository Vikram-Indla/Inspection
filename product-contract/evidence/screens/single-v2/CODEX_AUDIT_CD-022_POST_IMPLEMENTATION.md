## FAIL findings

### FINDING 1 — "Registry unavailable" negative path does not exist
- verdict: CONFIRMED
- evidence: `apps/web/src/app/planning/single/page.tsx:52-55` — `const { data: candidates } = await sb.from("factories")...` discards any `error` from the Supabase call; a failed query silently becomes an empty result set, rendered by `apps/web/src/app/planning/single/Wizard.tsx:160-162` as the generic "no factory matches" banner. No "registry unavailable" copy or retry control exists in either file.
- check: search with the Supabase connection artificially failing (e.g. temporarily invalid table name) and confirm the UI shows anything other than the plain "no match" banner — it does not.
- required correction: either implement the row's claimed neutral "registry unavailable + retry" state (check `error` from the query, branch UI accordingly) or correct `WIRING_MAP_CD-022.csv` row 1 to state this negative path is not implemented (`HANDOFF_BLOCKED` or a new decision), rather than leaving an unverified claim standing.

### FINDING 2 — Selection-time duplicate warning omits the visit ID and options the row and acceptance checklist require
- verdict: CONFIRMED
- evidence: `apps/web/src/app/planning/single/page.tsx:68` computes `duplicateVisitId`; `apps/web/src/app/planning/single/Wizard.tsx:24` types it into `GradedFactory`; `apps/web/src/app/planning/single/IdentityDossier.tsx:58-60` renders only the static `strings.duplicateWarning` string, never `factory.duplicateVisitId`. `grep -rn "duplicateVisitId" apps/web/src/app/planning/single/` shows zero consumers.
- check: search a factory with an existing active visit, open its dossier, and confirm the warning card names the conflicting visit or offers any action — it does not; compare to the publish-time block (`actions.ts:81`), which does include the visit ID.
- required correction: render `factory.duplicateVisitId` (and ideally a link/option, per `ACCEPTANCE_CHECKLIST_CD-022.md` line 13 "with cause (visit ID, status, rule)") in `IdentityDossier.tsx`'s duplicate banner, or narrow the wiring-map row's claim to match what actually ships.

### FINDING 3 — No page-level authorization guard on a planner-only screen; wiring row's claimed behavior is false
- verdict: CONFIRMED
- evidence: `apps/web/src/components/Shell.tsx:13-14` (auth-only check, no role check); `apps/web/src/app/planning/single/page.tsx` (no role query/branch); `apps/web/src/lib/shell-navigation.ts:1-4` (self-documented as non-enforcing); `supabase/migrations/0002_rbac_audit.sql:15` (`factories_read` open to any authenticated user). Contrast: `apps/web/src/app/planning/immediate/page.tsx:24-27` does implement an explicit role branch in the same codebase.
- check: sign in as a non-planner role (e.g. `inspector@mim.gov.sa`) and navigate directly to `/planning/single` — the full search/dossier UI renders; only the final publish write would fail via RLS, not a "no-data state 24" screen as the row claims.
- required correction: add an explicit server-side role check on `/planning/single` (mirroring `planning/immediate/page.tsx`'s pattern) that renders the claimed no-data/unauthorized state for non-planner roles, or correct the wiring row to describe the actual (RLS-write-blocked-but-UI-visible) behavior. This is a pre-existing gap CD-022 did not introduce, but it also did not close it, and the row's specific claim remains unverified-false either way.
