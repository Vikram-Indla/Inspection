## 3. Concrete P1 findings

1. **`decide()`'s `returned_sections` write is unvalidated against real section keys, which directly undermines the Scope Rail's "stored, never inferred" authority claim.** `apps/web/src/app/reviews/[id]/actions.ts:63,71`: `const sections = fd.getAll("returned_section").map(String);` … `returned_sections: decision === "return" ? sections : null`. The UI (`DecisionPanel.tsx:31-33`) only ever emits real keys via checkboxes bound to `sections.map(s => s.key)`, but the server action itself performs no server-side check that each submitted value is one of the current package version's actual `sectionsDef` keys, and the database column (`supabase/migrations/0001_foundation.sql:276`, `returned_sections jsonb`) carries no CHECK/enum constraint either. A crafted request (bypassing the checkbox UI) can persist arbitrary strings into `reviews.returned_sections`. CD-030's entire premise is that this column is the "SOLE authority" for expected/unexpected classification (`VersionCompare.tsx:6-12,82`); if it can be populated with a value that doesn't correspond to any real section, every subsequent changed answer whose real section doesn't happen to string-match that garbage value becomes classified `"unexpected"` (a false tamper alarm) — or, if the bogus value silently drifts from what the reviewer actually intended to return, a real out-of-scope edit could be misclassified. This is the same root defect the CD-029 independent audit already flagged (finding #2, "Decision enum and exact-section validation missing") and it is **still present, unresolved by CD-030's changes** — CD-030 reads and trusts this same unvalidated column as its tamper-evidence source of truth.

2. **The `decision` value itself is not allow-listed before being persisted verbatim.** `apps/web/src/app/reviews/[id]/actions.ts:61,68,70`: `const decision = String(fd.get("decision"));` is only checked via `["return","reject"].includes(decision)` (to require a reason) and `decision === "return"` (to require sections); anything else falls through to `status = "rejected"` while the raw, unvalidated `decision` string is written to the `decision` column unchanged. No CHECK constraint exists at the database level (`decision text` in `0001_foundation.sql:274`). This is inherited unchanged from CD-029 (same file) and remains open.

3. **Unauthorized access and a genuinely degraded data source are visually and textually identical, contradicting the WIRING_MAP's "not-found distinct"/"unauthorized distinct" claims (legs 1, 16).** `apps/web/src/app/reviews/[id]/page.tsx:15-38`: the `.single()` call on the joined `inspections` query returns a PostgREST error (`insErr` truthy) for zero matching rows regardless of *why* zero rows came back — a nonexistent id, an id an unauthorized user cannot see through RLS, and a genuinely degraded fetch all take the same `insErr`-truthy branch and render the same "Could not load"/"loadError" banner. The `!insErr` → "Not found" branch is very likely dead code in practice. This is the same shape of finding the CD-029 audit made independently about the same shared page (`page.tsx`).

4. **No client-visible role gating or AUDITOR badge exists, so an auditor is shown controls that will only fail after being clicked.** `apps/web/src/app/reviews/[id]/page.tsx:47,253-257`: `canStart` and the `open && ins.status === "under_review"` branch that renders `<DecisionPanel>` never inspect the viewing user's role — any authenticated user who can read the record (which RLS extends to auditor/ops/leadership) is shown a "Start review" button or a decision form. RLS (`reviews_insert`, `reviews_update`) will correctly reject an auditor's attempt server-side, but the UI gives no upfront indication of read-only/auditor status, matching STATE_MATRIX S10's unimplemented AUDITOR-badge requirement.

5. **The S11 loading-skeleton fix introduced a reproducible test race that the implementer's self-report did not catch.** `apps/web/e2e/cd-030-version-comparison.spec.ts:100-106` (`leg 4`) fails deterministically (reproduced twice, independently) because it reads page text via `.count()` immediately after navigation, without waiting past the new `loading.tsx` Suspense boundary added in commit `1b530af`. This directly contradicts the self-verification report's claim of "11 passed, 0 failed, 2 skipped" for the identical spec file on what should be the identical runtime state.

## 5. Overall conclusion

CD-030 is **not** production-ready as currently built, and it is **not** the clean pass the self-verification report and the WIRING_MAP CSV's per-leg "PASS" markings suggest. What is genuinely solid: the route-neutral consolidation (DEC-013-settled), the core stored-scope diff/classification algorithm, the honest presentation of the three deliberately-unimplemented comparison categories (media/package/metadata), the absence of any accept/merge control, RTL/keyboard/disclosure accessibility, and the S07 degraded-source fix — all independently verified against source and, where practical, a live browser run.

What blocks a clean PASS:

1. The Scope Rail's core integrity claim ("stored, never inferred") rests on a `reviews.returned_sections` value that is written by `decide()` with **no server-side or database-level validation** against real package section keys (P1 #1) — this is a direct, unresolved threat to the signature feature's trustworthiness, not a cosmetic gap.
2. The `decision` field has the same unvalidated-write problem (P1 #2), inherited from CD-029 and still open.
3. Unauthorized, not-found, and degraded-source states are not actually distinguishable to a user or an auditor, contrary to what the WIRING_MAP CSV claims for legs 1 and 16 (P1 #3).
4. There is no visible role/auditor signal in the UI (P1 #4, STATE_MATRIX S10, confirmed still open).
5. The live Playwright suite for this exact spec file does **not** pass cleanly as claimed — it fails reproducibly on leg 4, a defect introduced by this session's own S11 fix and not caught before being reported as "11 passed, 0 failed" (P1 #5).

None of this is a large rebuild. The fixes are narrow: (a) validate `returned_section`/`decision` server-side against the package's real section keys and an explicit decision enum before persisting (ideally also a DB CHECK constraint, mirroring the still-open CD-029 finding), (b) give the workspace an explicit unauthorized state distinct from not-found/degraded (e.g., a dedicated RLS pre-check or distinguishable PostgREST error code before falling back to the generic banner), (c) surface the viewing user's role/AUDITOR badge and hide mutating controls client-side in addition to the existing RLS enforcement, and (d) fix the leg-4 test to wait past the loading boundary (e.g. `await expect(page.getByText(...)).toBeVisible()` with Playwright's built-in retry, instead of a bare `.count()`).

**Recommended status: CONDITIONAL.** Do not certify CD-030 contract-complete until P1 findings #1–#4 are resolved (or explicitly deferred by a recorded decision, the way HANDOFF_BLOCKED_ACCEPT was) and the test suite passes live without the reproducible leg-4 failure. This report does not authorize implementation, merge, or deployment.
