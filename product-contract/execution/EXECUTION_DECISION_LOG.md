## D-001 — Daily-cap counting semantics

- A visit counts against an inspector's daily cap when ALL of the following hold:
  - the visit is assigned to that inspector (`assignments.inspector_id`);
  - `visits.planning_status = 'published'`;
  - the Execution Date matches: `coalesce(visits.execution_date, visits.window_start::date) = p_date` (Pre-Execution-selected Execution Date wins; the window start is the fallback until one is selected);
  - the linked inspection has NOT reached submitted-or-later: `coalesce(inspections.lifecycle_status, 'new') NOT IN ('submitted','under_review','approved','rejected','cancelled')` — submitted-or-later counts as completed and frees capacity.
- Cancelled visits never count: cancellation sets `planning_status = 'cancelled'`, excluding the row by the first predicate.
- Cap default is 10 (business-supplied), Admin-configurable via `engine_settings.execution.settings.daily_visit_cap`; the RPC falls back to 10 when the setting is absent.
- One shared server-side calculation (`public.inspector_daily_capacity` RPC); Planning publish and Pre-Execution wire to the same service in later phases. Callers must be planner, ops, or the inspector themself; anything else raises `insufficient_privilege`.

## D-002 — Stored 'prepared' ≡ canonical 'Ready for Execution'

- The canonical Operational State vocabulary is `new → ready_for_execution → on_the_way → arrived → executing → submitted → under_review`; virtual visits skip `on_the_way`/`arrived`.
- The persisted enum keeps its existing values; the stored value `'prepared'` remains the persisted Ready-for-Execution marker until writers migrate. Projection happens read-side via `projectOperationalState` (`apps/web/src/lib/execution/state-machine.ts`).
- No destructive rewrite of stored values. The enum was extended additively with `'under_review'` only.
- Inspection lifecycle is likewise a backward-compatible projection: new `inspections.lifecycle_status` column (backfilled and trigger-synced from the legacy free-text `status`); the legacy column and all existing read paths are untouched. Planning visit status NEVER gains `approved`.

## D-003 — Capability model (capabilities, not new roles)

- Implemented as `capabilities` + `role_capabilities` seed tables (22 capability keys; default role mapping) plus the `public.has_capability` RPC (security definer, `set search_path = ''`).
- Legacy roles are untouched and act as compatibility aliases: guards evaluate capabilities; role→capability resolution goes through `role_capabilities`.
- Catalogue tables are RLS-enabled, SELECT-only for authenticated; no write policies for app roles in Phase 1 — the governed grant/revoke UI is a later phase.
- `apps/web/src/lib/execution/capabilities.ts` mirrors the seed mapping for UI affordance only; the server RPC + RLS remain authoritative, and menu visibility is never authorization.

## D-004 — engine_settings writes stay direct-but-audited (no maker-checker)

- Phase 2A (`/admin/execution`) writes governed engine keys directly from capability-gated server actions: caller verified, `has_capability` RPC per section, payload validation, read-modify-write of only the governed keys, `version_label` bump + `updated_by`, and an `audit_events` row (`object_type 'engine_settings'`, `action 'execution_config_update'`, `requirement_refs ['EXE-ADMIN']`, before/after of the governed keys only).
- Maker-checker is deliberately NOT added to `engine_settings`: the platform precedent (`/admin/risk`, SCR-ADM-060) is a direct audited write, and the `engine_write` RLS policy (0002_rbac_audit.sql) already scopes updates to the admin role set. Layering a request/approval flow on top would change existing RLS and lifecycle semantics for every engine row, not just execution. Revisit if the sponsor requires dual control on configuration.
- Row-level audit: `engine_settings` already carries `trg_audit_engine_settings` from 0002_rbac_audit.sql; migration `20260721100000_execution_admin_audit.sql` verifies and idempotently re-attaches it if drifted. The `capabilities`/`role_capabilities` catalogues get NO row trigger: the original `audit_row_change` (0002) dereferences `new.id`, which fails on id-less tables; only the later hardened redefinition tolerates them. Catalogue grant/revoke is a later-phase governed flow; app-level `audit_events` rows are the record for this phase. (`audit_events.object_id` is `uuid`, so engine names travel inside before/after state rather than a fabricated uuid.)

## D-005 — offline retry/autosave values left unset (platform default)

- `engine_settings.execution.offline.max_sync_attempts` and `offline.autosave_interval_s` are NOT business-supplied, so Phase 2A ships them unset. Unset is an honest state: the current platform behavior applies and no number is invented.
- The control plane presents them as optional governed overrides — labelled "platform default" while unset, editable with validated bounds (1–100 attempts; 5–600 seconds) once the business supplies values. When every value is cleared the governed key is removed so absence stays truthful.
- This is the permitted configurable boundary of SAQEEL-EXE-CANONICAL-PLAN v1.0 §2: administration may govern the values, but their absence must fail closed rather than be fabricated.

## D-006 — grant-only capability overrides; guarded single-authority access changes

- Phase: 2B — governed role/capability grant-revoke (migration `supabase/migrations/20260721110000_execution_access_grants.sql`, `apps/web/src/app/admin/access/*`).
- **Grant-only overrides in Release 1.** `user_capability_grants` layers positive per-user grants ON TOP of role defaults; `has_capability` is the UNION of `user_roles → role_capabilities` and direct grants. There are deliberately NO negative grants (revoke-override semantics): a user keeps every capability their roles provide, and an override can only add. Revoking role-derived access happens by revoking the role, never by masking it. Negative grants would make the effective-access explainer non-conclusive (a capability could be present-yet-denied) and are deferred until a sponsor-approved contract defines their semantics.
- **Guards.** Every access RPC carries the self-escalation guard (`p_user` may never equal `auth.uid()` — no granting to or revoking from yourself, stable token `EXE-ACCESS-SELF`) and `admin_revoke_role` additionally carries the sole-security_admin guard (revoking `security_admin` is refused, token `EXE-ACCESS-LAST-SECURITY-ADMIN`, when the target is the last remaining holder of the role). All four RPCs are idempotent: granting an existing grant or revoking an absent one is a no-op success and writes no audit row.
- **security_admin remains the grant authority.** No new top-level role was created (D-003: capabilities instead of new roles); the four RPCs require `has_role('security_admin')` and both grant tables keep zero direct write policies — the security-definer RPCs are the only write path, so RLS stays authoritative and menu visibility is never authorization.
- **Audit.** Every actual change appends `audit_events` (`object_type 'user_roles'/'user_capability_grants'`, `object_id null` — the grant key is a composite pair, not a uuid, so it travels in before/after state per the D-004 precedent — `requirement_refs ['EXE-ACCESS']`). `user_roles` row writes are additionally covered by the pre-existing `trg_audit_user_roles` trigger; the app-level rows carry the governed action and requirement traceability.
- **Maker-checker deferred as a sponsor decision.** An approval workflow beyond the single-security_admin action (dual control for access changes) is a policy decision, not an engineering default — consistent with D-004 for configuration writes. The seams the page previously declared (separation-of-duties, self-escalation guard, approval + audit path) are now realized except the approval step, which stays a disclosed boundary until the sponsor requires it.


## D-007 — form_config optionality is fail closed

- Phase: 3A — Pre-Execution readiness backend.
- `visit_preparations.form_config.removed_optional_section_keys` may name ONLY sections the package definition **explicitly** marks removable: a section is removable iff it carries `optional: true` or `removable: true` AND does not carry `mandatory: true`. When the definition has no optionality metadata at all, NO removals are allowed — absent metadata is never read as "removable" (`EXE-PREP-MANDATORY-REMOVAL`).
- Rationale: the plan makes mandatory Forms/Action Forms unremovable, but the platform's package definitions do not yet carry a universal mandatory/optional vocabulary. Reading "not marked mandatory" as "removable" would fail open and let an inspector strip content Planning never declared optional. Failing closed means removals are impossible until the authoring side explicitly marks a section optional; nothing existing loses behavior because removal is a new Phase 3A capability.
- The same single validator (`private.execution_validate_form_config`) runs on save AND again on confirm, so a definition drift between save and Ready cannot smuggle an invalid composition into the snapshot. `added_action_form_template_ids` must reference published `configuration_templates` of `template_type 'action_form'`, with no duplicates inside the list or against the definition's own action forms (`EXE-PREP-DUPLICATE`, `EXE-PREP-FORM-INELIGIBLE`).

## D-008 — Ready creates the inspections row pre-journey with started_at NULL

- Phase: 3A — Pre-Execution readiness backend.
- `confirm_visit_ready` creates the `inspections` row if absent (`status 'in_progress'` → `lifecycle_status 'in_progress'` via the Phase 1 sync trigger; `package_version_id` = the resolved effective version; `started_at` stays NULL). The canonical plan requires Inspection Status In Progress at Ready, while the journey/session start remains the owner of `started_at` — the row existing pre-journey is how both statements hold. The field app's later Start Inspection finds the row already present (visits→inspections is unique per visit) and only sets `started_at`.
- Reopen (Ready → New) is allowed ONLY pre-journey (`operational_state = 'prepared'`; anything beyond raises `EXE-PREP-JOURNEY-STARTED`) and ONLY while no captured work exists: `started_at` NULL and zero `checklist_responses`/`evidence` rows (`EXE-PREP-WORK-CAPTURED` otherwise). Reopen regresses the inspection to `status 'not_started'` (lifecycle → `new` via the same trigger), resets the assignment to `assigned`, clears `confirmed_ready_at` and stamps `reopened_at`.
- Snapshot rows are NEVER touched by reopen: each Ready appends a new `visit_package_snapshots` row (`unique (visit_id, preparation_version)`), so the readiness history — including the exact resolved definition + sha256 checksum each Ready froze — stays complete and immutable (guard trigger, no update/delete policies). `visits.execution_date` and the saved draft survive reopen; the next confirm re-validates window/past/capacity at that moment.
- Idempotency: confirming while already ready returns the latest snapshot row without appending a duplicate; saving after Ready is refused outright (`EXE-PREP-REOPEN-REQUIRED`), so "already ready and nothing changed" is the only replay shape.

## D-009 — Planning publish evaluates the shared window capacity atomically

- Phase: 3A — Pre-Execution readiness backend.
- `publish_single_visit` and `publish_bulk_plan` (copied from `20260714091727_planning_publish_guards.sql` with every guard, advisory lock, STM-PLAN-001/002 transition, notification and idempotency behavior preserved byte-for-byte) now evaluate `inspector_window_capacity` over the whole visit window for the assigned inspector immediately after assignment creation. When no day in the window has remaining daily capacity, the publish raises `EXE-CAPACITY-WINDOW-FULL` and the entire transaction rolls back — bulk publication can never over-assign a date the inspector later cannot select, because publish and Pre-Execution date selection evaluate the SAME counting rule.
- The counting rule itself was factored into ONE private SQL helper (`private.execution_daily_used`, plus `private.execution_daily_cap` for the governed cap); `inspector_daily_capacity` keeps its exact Phase 1 signature/contract and is re-expressed over the helper, and `inspector_window_capacity` (per-day `used`/`remaining`, `has_availability`, same planner/ops/self caller guard) is built on it. The cap scan is bounded at 62 days: longer windows evaluate the first 62 days and report `truncated: true`.
- Known boundary, accepted for Phase 3A: within a single bulk publish, the batch's own visits are still `draft` while the per-assignment checks run, so the hook guards against already-published load (the over-assignment the plan targets) rather than intra-batch stacking; the pre-existing duplicate-active-visit and inspector-unavailable guards continue to prevent the same inspector receiving overlapping visits in one batch.
- `create_immediate_visit` is deliberately untouched in this phase.

## D-010 — Journey start requires confirmed readiness server-side

- Phase: 3B — Pre-Execution UI + readiness gating.
- `set_operational_state` (copied from 0015 with every guard, leg and the idempotent-replay behavior preserved) now refuses the `on_the_way` leg unless the visit has a confirmed preparation (`visit_preparations.confirmed_ready_at IS NOT NULL`), raising the stable token `EXE-READY-REQUIRED`. Readiness itself is produced only by `confirm_visit_ready`, which re-validates assignment, `execution.prepare`, Execution Date, mode eligibility, package resolution and form composition before stamping it — so the journey guard can never be satisfied by an unvalidated state.
- Arrived/executing legs need no re-check: they are unreachable without a prior `on_the_way`, so they inherit the guard transitively. Idempotent replay (`cur = p_next`) returns before the check, keeping offline retries safe.
- The virtual execution lane is unaffected: virtual visits skip the `on_the_way`/`arrived` pair (plan §7) and no virtual code path calls this RPC for that leg (verified — the only caller is the physical Startup lane via `transitionOperationalState`).
- The field UI gates earlier and more gently (package download + Start Journey stay disabled with the reason visible until Ready), but the database guard is the authority: no client-side bypass can start a journey without Ready.

## D-011 — Start Inspection reuses the inspections row created at Ready

- Phase: 3B — Pre-Execution UI + readiness gating.
- `confirm_visit_ready` creates the `inspections` row at Ready with `started_at NULL` (D-008). The field Start Inspection step now selects the existing row for the visit first and, when found, reuses it: `started_at` is set only when still null (`UPDATE ... WHERE started_at IS NULL`), because the journey/session start owns that timestamp and an existing value must never be clobbered. The blind insert is kept only for the legacy path where no row exists, so the write stays idempotent on the `visits -> inspections` unique key.
- The resume affordance and the pre-start confirmation card now key off the actual start marker (`started_at IS NOT NULL`) rather than the row's mere existence. For legacy rows (which only ever existed after Start Inspection) the conditions are byte-equivalent to the previous `status <> 'not_started'` checks; for Ready-created rows they keep the four-step flow intact instead of offering a premature "Resume inspection".

## D-012 — Journey start is a single atomic RPC; overdue-inside-window allowed with audit

- Phase: 4A — Physical Journey, Cancellation & Location backend (migration `supabase/migrations/20260721140000_execution_journey_cancellation.sql`, wrappers `apps/web/src/lib/execution/journey.ts`).
- `start_journey(p_visit, p_device)` is the ONE atomic start path (plan §11): in a single transaction it validates assignment + `execution.start_journey`, Published visit, confirmed Ready preparation (stable token `EXE-READY-REQUIRED`, shared with Phase 3B), window timing, frozen package availability/integrity (sha256 recompute of the latest `visit_package_snapshots.definition::text` against its stored checksum — `EXE-JOURNEY-PACKAGE-MISSING` / `EXE-JOURNEY-PACKAGE-INTEGRITY`), resolved dispatch coordinates (`coalesce(visits.planner_*, factories.official_*)` — `EXE-JOURNEY-LOCATION-MISSING`) and device provenance (`device_id` + `application_version` mandatory — `EXE-JOURNEY-DEVICE-MISSING`; OS/network tolerated absent and recorded honestly). It then flips the visit On the Way through the governed `set_operational_state` leg (RBAC-009 + legal legs + D-010 readiness stay the single authority), inserts the journey with server/device timestamps and the preparation/checksum/overdue facts in `prestart`, writes the first `telemetry` geo_event when a full GPS fix was supplied, and audits (`journey_start`, `requirement_refs ['EXE-JOURNEY']`). No partial journey survives a failed start — one function, one transaction.
- Idempotency is plan-exact: an existing active journey (`uq_journey_active_per_visit`) is RETURNED (`reused: true`) for multiple clicks/retries, and a `unique_violation` race between concurrent starters resolves to the same return. The direct browser `journey_sessions` insert in `field/[visitId]/Startup.tsx` becomes legacy with this decision; the UI migrates to the RPC in Phase 4B.
- Timing (§8, governed `engine_settings.execution.journey_start_timing = 'inside_visit_window'`): `now()` outside `[window_start, window_end]` is blocked (`EXE-JOURNEY-OUTSIDE-WINDOW`); after the Execution Date but inside the window is ALLOWED with the overdue flag in `prestart` and a separate `journey_start_overdue` audit row.
- `geo_events` gains ONE nullable provenance column (`source`) because the plan requires every location fact to carry its source and the table had none; historical rows stay null.

## D-013 — Active-session cancellation is request+decide; pre-start keeps the flag flow; nothing captured is ever deleted

- Phase: 4A (same migration).
- On the Way / Arrived / executing, the inspector files a `cancellation_requests` row via `request_active_cancellation` (guarded `execution.request_active_cancel`; phase derived from `operational_state`; governed `engine_settings.field.cancellation_reasons` keys — `EXE-CANCEL-REASON`; comment mandatory for `other` — `EXE-CANCEL-COMMENT`; idempotent on a caller-supplied `idempotency_key`). Pre-journey visits deliberately keep the existing `request_visit_cancellation` flag flow (0020_fix_field_journey, preserved) — the new RPC refuses them with `EXE-CANCEL-USE-PRESTART`.
- The terminal transition belongs exclusively to `decide_active_cancellation`, gated by `operations.approve_active_cancel`. The requester may NEVER decide their own request (`EXE-CANCEL-SELF-DECIDE`, even when they also hold the operations capability — same separation-of-duties rule as `decide_geo_override`). Deciding is idempotent-safe: replaying the same decision returns the current state; a conflicting decision on a closed request fails closed (`EXE-CANCEL-DECIDED`). Rejection requires a reason (`EXE-CANCEL-DECISION-REASON`) and leaves the visit completely unchanged.
- Approval is terminal and atomic in ONE transaction: request approved; other pending requests for the visit superseded (`status 'cancelled'`, kept for history); `visits.planning_status = 'cancelled'` with `cancellation_reason` recorded (FLD-VIS-006); active journeys `completed` with `ended_at` (tracking/sessions stop); non-submitted inspections `status = 'cancelled'` (the Phase 1 sync trigger already maps cancelled → cancelled, verified — no trigger change needed); `assignments.status = 'returned'` with `return_reason`, which FREES the inspector's schedule and daily capacity (the shared `private.execution_daily_used` counter excludes cancelled inspections and non-published visits). Captured data — responses, evidence, geo_events, package snapshots — is PRESERVED: the migration contains no delete of any of it. No compliance fields are touched, and a cancelled visit never becomes a submitted inspection.
- `cancellation_requests` is RPC-write-only (no insert/update/delete policies; requester reads own, ops/planner/leadership read all) and every request/decision appends `audit_events` (`requirement_refs ['EXE-CANCEL']`) plus inspector notifications (`cancellation_approved` / `cancellation_rejected`) and an ops/planner fan-out on request.

## D-014 — Five distinct location facts; corrections append-only; outside-arrival is a notice, never a silent override

- Phase: 4A (same migration).
- The location model keeps five facts separate (plan §13): the registered master location (`factories.official_*`, Senaei-owned), the Planning visit location (`visits.planner_*`), the journey start location (first `telemetry` geo_event, `source 'journey_start'`), the arrival location (`arrival` geo_event, `source 'confirm_arrival'`) and the corrected visit location (`visit_location_corrections`) — each with source, actor, timestamp, accuracy and online/offline capture context.
- `correct_visit_location` (guarded `execution.arrive`; reason mandatory — `EXE-LOCATION-REASON`; range-checked — `EXE-LOCATION-RANGE`) is INSERT-only into the append-only corrections table (guard trigger blocks update/delete; no write policies; audit carries before = current effective coordinates + their source, after = corrected). It NEVER updates `factories` or `visits.planner_*`: corrections apply to the current visit only, and original and corrected remain visible side by side. Corrections are accepted pre-submission (prepared/on_the_way/arrived/executing for the record).
- `confirm_arrival` captures server/device time + GPS, enforces the governed accuracy gate (`gis.gps_accuracy_checkin_max_m` — `EXE-ARRIVAL-ACCURACY`), and evaluates the fence against the EFFECTIVE target — the latest correction when one exists, else the registered/planning location — with radius `coalesce(factories.geofence_radius_m, gis.arrival_detection_radius_m)`. Inside: arrival geo_event (with `gis_version` from the engine row's `version_label`), tracking stops (`journey_sessions.status 'arrived'` + `ended_at` — plan §13 "stops travel tracking", harmonizing M04-055/DEC-002: no location collection during the inspection itself), the governed `set_operational_state` leg sets Arrived, and an `arrival_confirmed` audit row records observed vs target. Outside: NOTHING mutates — the RPC returns `{result:'outside', distance_m, notice:'EXE-ARRIVAL-OUTSIDE'}` and the only paths forward are retry, governed correction, or the existing Operations geo-override approval flow. No silent override exists anywhere in the arrival path.

## D-016 — Active-session cancellation is non-blocking for the inspector until decided; workspaces lock only on approval

- Phase: 4B (same files).
- During an active session (on_the_way / arrived / executing), the inspector files a cancellation REQUEST (`request_active_cancellation`, idempotency key generated once per mounted component so retries replay the same request) and KEEPS WORKING: the startup and the workspace show a non-blocking "awaiting Operations decision" banner and poll the server-rendered state (15s refresh, same pattern as the geo-override pending state). ## D-017 — Item lifecycle lives in inspection_item_states; deselected stays in audit, excluded from the denominator; restore is pre-submit only

- Phase: 5 — Execution workspace item lifecycle, canonical compliance, violation candidates (migration `supabase/migrations/20260721150000_execution_item_lifecycle.sql`; `field/inspection/[id]/runtime.ts`, `Workspace.tsx`, `page.tsx`; `lib/offline.ts`).
- Per-visit item scope is a NEW composite-PK table `inspection_item_states (inspection_id, item_id)` with `state 'added' | 'deselected'`, `reason`, `actor`, `created_at`, `reverted_at`. A state is ACTIVE while `reverted_at IS NULL`. Deselect REQUIRES a non-empty reason (`inspection_item_states_reason_shape` check); add allows a null reason. RLS mirrors the `responses_rw` approach (0002): read for the assigned inspector plus reviewer/auditor/ops/planner/leadership; insert/update for the assigned inspector of the parent visit ONLY; NO delete policy anywhere. The submitted/under_review/approved/rejected lock reuses `guard_submitted_inspection` verbatim (it keys off `coalesce(new.inspection_id, old.inspection_id)`, so it attaches unchanged to insert/update/delete).
- `audit_row_change` (0002) is NOT reusable here: it dereferences `new.id`/`old.id` and this table has no `id` column. An equivalent composite-key trigger `audit_item_state_change` appends the same `audit_events` shape keyed by `inspection_id` with the full row in before/after state.
- Outbox: ONE new op kind `item_state` carries the DESIRED final row (state/reason/reverted_at) and replays as an upsert on `(inspection_id, item_id)`, so FIFO sequences of add → deselect → restore converge idempotently; duplicate replays are harmless. `mim-field-v1` schema unchanged — ops are records in the existing store.
- Effective item set (runtime `effectiveSections`, §15): snapshot default items MINUS actively deselected PLUS actively added. An added item already in the snapshot is a no-op (dedupe by code). Added items land in a synthetic `__added` "Added items" section because the frozen definition references items only as code lists inside sections — no item→section metadata exists outside those lists. Deselected items require no response/evidence, create no violation, and are excluded from the compliance denominator; they remain visible in a collapsed "Deselected (N)" audit list with their reason, and `item_states` also rides the immutable submission snapshot.
- Deselect affordance: OPTIONAL items only — requirement resolves as `response_model.requirement ?? definition.item_rules[code].requirement ?? 'required'`, so absent metadata FAILS CLOSED as mandatory (same rule as D-007); inspector-added items can always be removed again. Restore sets `reverted_at` via the same op and is available BEFORE SUBMIT only; under a reviewer return, restore/deselect unlock only for items whose home section is in the return scope, and the library panel locks entirely (added items have no frozen section to match — fail closed).

## D-018 — Violation candidates are INVALIDATED, never deleted, on Compliant flip; dependent trigger-generated action forms are cancelled in the same outbox replay

- Phase: 5 (same files).
- `violations` gains three nullable columns (`invalidated_at`, `invalidated_by`, `invalidate_reason`) and stays insert-only: a narrow guard trigger `guard_violation_invalidate` permits UPDATE exclusively when no column other than the three invalidation columns changes, refuses to ever CLEAR an invalidation (no un-invalidate — audit preserved), and applies the same parent lock list as `guard_submitted_inspection`. A partial index `violations_active_inspection_idx (inspection_id) where invalidated_at is null` serves active-candidate lookups.
- When a response flips away from a violation-mapped value (§18), the workspace enqueues a `violation_invalidate` op (reason "Response changed to compliant") AFTER the response op, so FIFO replay invalidates only after the new response lands. The op targets the violation by id when known, else the ACTIVE candidate for `(inspection_id, violation_code_id)`; zero affected rows is a legitimate no-op (the candidate never synced). Re-triggering the violation later creates a FRESH candidate: `ensureViolation` reuses only `invalidated_at IS NULL` rows (tolerant fallback to the unfiltered read pre-migration), and the UI keeps invalidated candidates VISIBLE with an "Invalidated" state in the violations list plus `invalidated_violations` in the submission snapshot.
- Dependent action-form re-evaluation mechanism (exact): inside the `violation_invalidate` replay handler, immediately after stamping the violation, the replay runs `action_forms.update({ status: 'cancelled' }).eq('violation_id', vid).eq('status', 'open')`. `action_forms.status` is free text (no enum/check forbids 'cancelled', verified against 0001 + 0015), so no schema change was needed. ONLY trigger-generated forms LINKED to the invalidated candidate are closed; mandatory PACKAGE-INCLUDED forms (`violation_id` null) are NEVER touched. Client-side, the flipped answer also makes `formRequired` return null, so the form instantly leaves blockers/progress; the server row is closed by the replay, and `audit_row_change` on action_forms records the before/after.
- Penalty singularity (fail closed, defense-in-depth): `penalty_mappings.violation_code_id` is UNIQUE (one-penalty Phase 1), but the page previously took the first row unconditionally. ## D-019 — Preliminary Compliance Rate pinned to plan §20; computeHealthScore signature preserved

- Phase: 5 (runtime.ts).

An item is SCORED when `response_model.scoring_enabled !== false`, `score_weight > 0` (weight zero/absent = non-scoring), the answered value is not in `score_excluded_on` (existing `scoreExcluded` na handling), and the value's mapping result is compliant/non_compliant. ## D-020 — Server-authoritative version numbering + the exact returned-scope comparison rule

- Phase: 6 — Submission + Review hardening (migration `supabase/migrations/20260721160000_execution_submission_review.sql`; `lib/offline.ts`; `field/inspection/[id]/Workspace.tsx`, `page.tsx`).
- **Version numbering moves server-side.** `submit_inspection` takes a row lock on the `inspections` row (`SELECT ... FOR UPDATE`) and computes `max(version_number)+1` under it, so two offline devices can never pick the same number — the client-side `max+1` in the legacy outbox path was a hard-fail race (both devices collide on `unique(inspection_id, version_number)`, and the legacy duplicate-tolerance could mask that collision as success). The client keeps its number ONLY as legacy-fallback payload for pre-migration servers and the optimistic queue message; after an RPC submit, local state follows the returned `version_number`.
- **Returned-scope comparison rule (exact).** On RESUBMISSION only — when a decided `decision='return'` review with non-null `returned_sections` exists (latest by `decided_at`; `returned_sections` is the sole scope authority) — every section key in the new snapshot's `sections` map that is NOT in the returned scope must be byte-identical to the latest prior version: the per-section sub-objects `{answers, notes, dates, evidence}` are compared with jsonb `=` (canonical equality after jsonb normalization — key order/whitespace-insensitive). Evidence-manifest entries are compared by `{id, sha}` (never URLs) on id-sorted arrays, and only when BOTH snapshots carry per-section evidence — legacy prior snapshots without per-section structure are sliced from their flat code-keyed `answers/notes/dates` maps using the CURRENT snapshot's `section_items` membership (stable because `package_version_id` is frozen per inspection, FLD-INS-003) and compare on responses only. Any mismatch raises `EXE-SUBMIT-SCOPE-VIOLATION` naming the offending section keys; first submissions (no return review) skip the check entirely.
- **No masking.** RPC guard failures (`EXE-SUBMIT-*`) surface as explicit failed-sync states; the legacy duplicate-tolerance applies ONLY inside the 42883 legacy-fallback branch, never to RPC errors.
