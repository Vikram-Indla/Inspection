The architecture

Five layers, loaded low to high and removed high to low

The load order is the whole design. Reference data is verified and never written. Policy comes before master data because a factory without a published package version cannot be planned against. Journeys come last because every journey needs a factory, an inspector and a package to exist first. Unload runs the ladder in reverse, which is the only order that never violates a foreign key.

The unit

One inspection journey, stopped at a chosen point

Every screen in the product is the same object seen at a different moment. Planning shows journeys before assignment; Operations shows them in motion; Execution shows them being filled in; Reviews shows them awaiting a decision; the dashboard aggregates the ones that finished. So the atom of test data is not a table row — it is a journey and the stop at which it stopped moving. That one choice determines every physical row it creates.

Identity

Every row's key is derived, which is what makes unload possible

The unloader does not search for rows that look synthetic. It recomputes exactly the same keys the loader computed and deletes those, and nothing else.

uuidv5(seed_batch_id, "<table>:<logical key>")

uuidv5(batch, "factory:F-RUH-0042")   → always the same factory id for this batch
uuidv5(batch, "journey:JRN-RUH-00417")
uuidv5(batch, "resp:JRN-RUH-00417:SAFE-014")
  • Re-running the loader is idempotent. The same logical key gives the same UUID, so a second run upserts instead of duplicating.
  • No canonical table needs a new column. The earlier discovery design proposed adding seed_batch_id to forty tables or maintaining a join table. Neither is needed.
  • Nothing is ever deleted heuristically. A row is removable only if its id appears in the batch manifest.

One new table is required: seed_runs, the ledger of what was loaded, when, by whom, and at which anchor date. Its shape is already specified in the seeding-discovery pack and is adopted unchanged, plus a cleaned status.

Operations

Load, verify, unload

# load
npm run testdata:preflight
npm run testdata:load    -- --profile demo --anchor 2026-08-22
npm run testdata:verify  -- --batch <id>

# inspect
npm run testdata:status

# unload
npm run testdata:unload  -- --batch <id> --dry-run
npm run testdata:unload  -- --batch <id> --confirm
npm run testdata:unload  -- --all --confirm   ← the whole-data unload
  1. Preflight writes nothing. It refuses any host off the non-production allowlist, refuses NODE_ENV=production, checks migrations are current, and confirms L0 is present and unmutated.
  2. The batch is registered before the first write. A row in seed_runs marked in_progress, so a run that dies halfway is still identifiable and still removable.
  3. The anchor date generates twelve months backwards. About 40% of approved journeys land inside the rolling 30-day analytics window; about 25 are dated today so the live map and the operational tiles are not empty during a demo.
  4. A run that cannot write its manifest fails. An unmanifested batch would be unremovable, so the manifest is a completion condition, not a byproduct.
  5. Verify is the artefact the training team needs. It walks the screen map asserting one expectation per row and reports which screens are still empty and why.
  6. Dry run always comes first. Zero writes; prints exactly which tables and how many rows would go.
  7. Deletion runs the ladder in reverse — removable L4, then L3, L2, L1 — by explicit row id. It stops at the first row still referenced from outside the batch and reports it rather than cascading.
  8. The audit trail survives. Append-only tables are excluded by allow-list, not by a filter. The batch's audit trail stays as a permanent record of what happened, which is also what makes the unload auditable.
  9. Partial failure does not auto-rollback. The batch stays partial and a person decides: resume it, or unload it and start again.

And four open decisions this design does not resolve

  • Demo target values. 82% compliance, 68% coverage, 5.8% cancellation are shape targets for a believable demo — not governed thresholds. They need sign-off before the loader treats them as goals.
  • Penalty amounts. Must come from approved penalty_mappings. If those are unpublished, penalty journeys stop at the violation and the penalty stays absent.
  • Retention. No expiry is proposed for seed batches; they persist until someone unloads them.
  • The non-production allowlist. The exact host set preflight accepts must be named and stored outside this repository.
